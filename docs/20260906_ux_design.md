## 1. Who this is for

### Primary persona: the self-coached athlete

> An experienced athlete who writes (or at least steers) their own training program. They understand RPE, volume, and deloads. They train across multiple disciplines (strength + endurance + misc). They have been injured before — usually from doing too much, too fast, too repetitively. They want the *signal* from sport science without the *lifestyle* of sport science: no weekend Excel sessions, no gram-precision program design, no medical cosplay.

Secondary: the data-curious recreational athlete (same needs, lower training age). Explicitly **not** for MVP: coaches managing other people, beginners needing guidance on *how* to train.

### Design consequences of this persona

- They don't need to be taught what RPE means. **No onboarding tutorials about concepts.**
- They don't want to be coached by an algorithm. **We surface signals; they make decisions.**
- They will forgive missing features. They will not forgive friction in logging. **Speed is the product.**
- They already have a program in their head. The app doesn't plan; it **records and reflects**.

### Jobs to be done

> Format: *When I [situation], I want to [motivation], so I can [outcome].*

1. **J1 — Log without breaking flow.** When I'm between sets at the gym, I want to record what I just did in seconds, so I can get back to training.
2. **J2 — Start instantly.** When I walk into the gym / head out the door, I want to start logging immediately, so I don't lose momentum.
3. **J3 — Know how today fits the week.** When I open the app, I want to see where this week is heading, so I can decide what today should be.
4. **J4 — See progression.** When I review my training, I want to see how my load and my strength are trending over weeks and months, so I know whether my program is working. *Is my weekly load building? Is my squat progressing — and is my leg strength progressing? Are my pressing numbers stalling?*
5. **J5 — See balance.** When I review my training, I want to see where my time and stimulus actually go across regions and disciplines, so I can spot neglect before it becomes weakness. *Am I doing enough prehab? Did legs get a fair share this month, or did climbing eat everything?*
6. **J6 — Catch trouble early.** When my training is drifting toward overload or a niggle is becoming a pattern, I want to be told plainly, so I can adjust before I'm injured.
7. **J7 — Trust the record.** When I look back, I want an accurate, complete log of what I did, so I can reuse sessions and see real progression.
8. **J8 — Check in without a ritual.** When I wake up, I want to record sleep and how I feel in under 20 seconds, so the data exists without me thinking about it.
9. **J9 — Record pain the moment it appears.** When something hurts, I want to pin it to a body region immediately, so the trend data exists later when I need it.

These jobs are ordered by priority. When in doubt, J1 and J2 win. J4 and J5 together are the *reason the logging exists* — the payoff loop. J6 is a guardrail, not the product's purpose.

## 2. Core loops

The app is four repeating cycles. Screens are just where loops happen. If each loop is satisfying, the app succeeds.

### Loop 1 — The Daily Loop (every day)

```
Open app → (optional) 20-second check-in → see today in context → done
```

Success: the check-in takes < 20s, is never forced, and the home screen always answers "where am I this week" in a glance.

### Loop 2 — The Logging Loop (every training day, in the gym)

```
Start workout → add exercise → log set → log set → … → finish → rate effort → close
```

This is the heart of the product. Success: a familiar set costs ≤ 4 taps; the whole interaction feels like jotting in a notebook; finishing feels like closing the notebook — satisfying and brief.

### Loop 3 — The Progress Loop (roughly weekly) — *the payoff loop*

```
Open Insights → how is my training progressing? (load, strength, balance)
→ scan attention signals if any → form an intention for the week
```

This loop is why all the logging exists. The first questions it must answer, in order: **Am I progressing?** (load trend, strength trends) → **Am I balanced?** (region mix incl. prehab) → **Is anything drifting wrong?** (signals). Not the other way around.

Success: the user leaves with an *assessment* ("legs are coming up nicely, but pressing has stalled and prehab disappeared") and a *decision* ("get a leg session in, swap a press variation") — not just numbers.

### Loop 4 — The Alarm Loop (occasional, high value)

```
Something hurts → log pain in ≤ 4 taps → app connects it to training patterns → user adapts
```

Success: pain logging is so cheap that it actually happens, and the app is the thing that notices "this is the third shoulder complaint this month."

## 3. Information architecture

### The structural fix

The current app's core IA problem: **the tab named "Log" does not let you log.** Logging is not a place you *go*; it's a mode you *enter*. So:

- **Three tabs:** Today · History · Insights.
- **Logging is a full-screen flow** launched from Today (or History), not a tab. While a workout is in progress, a persistent mini-bar sits above the tab bar on every tab — one tap returns to the workout.

```
┌─────────────────────────────────────────────┐
│  TABS (places you go)                       │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐      │
│  │  Today  │  │ History │  │Insights │      │
│  └─────────┘  └─────────┘  └─────────┘      │
│                                             │
│  FLOWS (modes you enter, overlay everything)│
│  ┌───────────────────────────────────────┐  │
│  │ Active Workout  (full screen)         │  │
│  │ Check-in sheet  (bottom sheet)        │  │
│  │ Pain sheet      (bottom sheet)        │  │
│  │ Finish sheet    (bottom sheet)        │  │
│  └───────────────────────────────────────┘  │
│                                             │
│  PUSHED SCREENS (drill-in, standard nav)    │
│  └─ Session detail (from Today or History)  │
└─────────────────────────────────────────────┘
```

### Screen job statements

Every screen has exactly one job. If a screen is doing two jobs, split it.

| Screen | Its one job |
|---|---|
| **Today** | Answer "what now?" — check in, start/resume training, see this week at a glance. |
| **Active Workout** | Record what is happening right now, as fast as possible. |
| **Exercise Picker** | Get the right exercise onto the workout in ≤ 2 taps. |
| **Finish sheet** | Close the session: confirm duration, capture sRPE, optional feeling. |
| **Check-in sheet** | Capture today's wellness in < 20 seconds. |
| **Pain sheet** | Pin a pain to a body region and severity, fast. |
| **History** | Find any past session and reuse it. |
| **Session detail** | Show one session completely; offer reuse. |
| **Insights** | Answer "how is my training going?" — progression, balance, then attention signals. |

### Navigation rules

- Tab bar: exactly three items. No badges except a warning dot on Insights when an un-dismissed high-priority signal exists.
- Active Workout can be minimized (swipe down or tap collapse) → it becomes the persistent mini-bar. It is never destroyed by navigation.
- Session detail is a pushed screen with a back button — not a tab, not a modal.
- The user can reach the Active Workout from any tab in exactly 1 tap (via mini-bar) when a session is live.

## 4. Flows with budgets

Budgets are design targets, measured on a familiar device. "Taps" exclude typing; typing costs are stated separately.

### F1 — First run / onboarding

```
Install → create account (email) → land on Today (empty state) → Start first workout
```

- No concept tutorials, no carousel, no "what is RPE" screens. The persona knows.
- One optional question allowed during first workout finish: none. Everything has a default.
- Empty states are motivational in tone (see §8).

**Budget:** account creation ≤ 60s. First workout startable immediately after.

### F2 — Daily check-in (Loop 1)

```
Today screen shows check-in card (first open of the day, if not yet done)
  → tap "Check in" → bottom sheet
  → 4 core rows: Sleep duration · Sleep quality · Fatigue · Soreness
  → "More" expander: Stress · Motivation · HRV · Body weight · Note
  → every row optional; tap "Save"
```

- **Budget:** ≤ 20 seconds for the 4 core rows; 1 tap to save; 1 tap to dismiss ("Not today").
- Sleep duration uses a stepper (± 15 min), not a text field.
- 1–10 values use a horizontal numbered selector, one tap per row. No sliders (finicky), no typing.
- Defaults: empty. We do not pre-fill from yesterday — stale data is worse than no data.
- If dismissed, the card collapses to a quiet "+ Check in" line at the bottom of Today. It never nags.
- Post-session variant (F7) writes to the *same* daily log — one per date, as the data model requires.

### F3 — Start a workout (Loop 2 entry)

```
Today
  → tap "Start workout"                       (primary, full-width)
      → Active Workout opens, blank, timer running
  — or —
  → tap "Repeat: Push day (Tue)"              (secondary row, if a recent session exists)
      → Active Workout opens with that session's exercises pre-loaded, sets blank
```

- **Budget:** 1 tap to a blank workout; 1 tap to a template-loaded workout.
- No type picker, no setup screen. The session *type* is inferred from the exercises added (and editable at finish if wrong). The user thinks in exercises, not categories.
- If a workout is already in progress, the primary button is "Resume workout" and the mini-bar is visible. There can only be one active workout.

### F4 — Log a familiar strength set (the most important flow in the app)

```
Active Workout
  → tap "+ Add exercise"                                  (tap 1)
  → picker opens instantly: recents first, no typing needed
  → tap "Bench Press"                                     (tap 2)
  → exercise block appears:
      fields blank (user preference: no pre-fill)
      ghost reference line: "Last: 80kg × 8, 80kg × 8, 80kg × 6"
  → tap the ghost line to adopt last values  — or — type weight + reps
  → tap ✓ to log the set                                   (tap 3–4)
```

- **Budget:** ≤ 4 taps + at most 2 typed values. (The old doc's "3 taps" assumed pre-filled values, which the user explicitly rejected. 4 taps with one-tap-adopt is the honest cost of blank-default, and it is worth paying — blank fields invite correct data; pre-filled fields invite lazy confirmations.)
- The ghost reference line is *information*, not a default: it answers "what did I do last time?" without putting a thumb on the scale.
- Set logging gives a small haptic + the ✓ fills in. This is the app's one celebratory micro-interaction; keep it subtle.
- Next empty set row appears immediately after logging. Logging the same thing again = one tap on ✓ (row inherits nothing, but keyboard remembers position — fields focus in order: weight → reps → RIR).
- RIR is optional and hidden per set behind a small "＋RIR" affordance; once used on an exercise, it stays visible for that exercise.

### F5 — Log an endurance session

```
Active Workout
  → "+ Add exercise" → tap "Run" (recents)
  → fields follow the exercise's history: distance · duration · pace
      (inferred from last logged set for that exercise name)
  → enter values → ✓
  → Finish → rate effort → Save
```

- Field set per exercise is inferred from its last logged set: if last time had distance/duration, show those; if weight/reps, show those. Unknown exercises default to weight/reps with a one-tap "switch to distance/time" toggle.
- Interval sessions: multiple sets on one exercise entry (set = interval), matching the data model.

### F6 — Log pain (Loop 4 entry)

Entry points (all equal citizens): quiet "+ Pain" link on Today · button in Active Workout footer · post-session option in Finish sheet.

```
Pain sheet
  → body region: horizontal chips (recent/suggested regions first) + free text   (1 tap)
  → severity: 1–10 numbered selector                                             (1 tap)
  → optional note
  → Save                                                                         (1 tap)
```

- **Budget:** ≤ 4 taps, ≤ 15 seconds.
- Region chips suggest from the user's own history (their free-text regions), not a medical diagram. (A body silhouette picker was in the old doc — deferred; chips are faster and match the free-text data model.)
- Severity anchors shown: 1 "annoying" — 5 "affects training" — 10 "can't train".

### F7 — Finish a workout (Loop 2 exit)

```
Active Workout → tap "Finish"
  → Finish sheet:
      Duration   47 min      (auto from timer, editable)
      How hard was it?  1 ··· ⑩   ← required, one tap. Anchors: 1 "very easy", 10 "max effort"
      Feeling (optional):  [Good] [Tired] [Something hurts → pain sheet]
      Note (optional)
  → "Save workout"
  → returns to Today. Week strip updates (+1 session). No fanfare screen.
```

- **Budget:** ≤ 3 taps (Finish → effort → Save).
- **Why effort is required here:** the API needs `srpe` to compute load — it is the fuel of every downstream signal. This is the *single* gated input in the entire app, and it costs one tap. Justified.
- "Quiet completion": no confetti, no share card, no rating guilt. A logged session is its own reward.
- Post-session feeling writes to today's daily log (fatigue/notes), never blocks saving, dismissible with one tap.

### F8 — Reuse a previous session

```
History → tap session → Session detail → "Log again" → Active Workout
  with exercises pre-loaded (sets blank, ghost references from that session)
```

- **Budget:** 3 taps.
- Exercises can be removed or reordered before logging the first set.

### F9 — Progress review (Loop 3)

```
Insights tab
  → top: "How's training going" — 8-week load trend with a one-line verdict
        ("building steadily", "flat for 3 weeks", "spiking")
  → strength progression: your key exercises, trend arrows + sparklines
  → balance: region mix incl. prehab share, vs. your own history
  → attention signals: 1–3 plain-language cards, only if something needs it
  → user forms an intention; nothing else required
```

- **Budget:** the glance must answer "am I progressing?" in ≤ 5 seconds without any tap.
- Progression first, signals second — signals interrupt the progression view, never replace it.
- Signal cards are capped at 3. If there are 5 things to say, say the 3 most important. Attention is the scarcest resource in this app.
- Every progression block and every card expands to the underlying numbers ("the why"). Transparency is how a self-coached athlete learns to trust the app.

### F10 — Respond to a warning (Loop 4 exit)

```
Signal card, e.g. "Pressing volume high while shoulder pain is trending up"
  → tap → detail view: pain trend line + pressing volume trend, overlaid
  → suggested action in hedged language ("Consider swapping pressing
     variations or trimming pressing volume this week")
  → [Log pain again]  [Dismiss]  — no forced behaviour change
```

- The app never prescribes and never scolds. It presents the coincidence of trends; the self-coached athlete connects the dots.

## 5. Interaction principles

Non-negotiable rules. Every screen obeys them. Numbered for reference in code reviews.

- **P1 — Logging speed above all.** Every design decision in the Active Workout is resolved in favour of fewer taps and less typing. Measure: familiar set ≤ 4 taps; cold-open → first exercise ≤ 10 seconds.
- **P2 — One screen, one job.** No screen does two things. (Fixes the current "Log tab that is a dashboard".)
- **P3 — Blank by default, memory on demand.** Fields start empty. History appears as *recalls you can adopt with one tap*: recents lists, ghost reference lines, autocomplete while typing. Never as silently pre-filled values.
- **P4 — Recents first, always.** The user should almost never type to find something they've used before. Typing is for *new* things.
- **P5 — Inline everything.** Editing sets, durations, and values happens in place. Sheets/modals only for genuinely distinct sub-tasks: exercise picking, check-in, pain, finish.
- **P6 — Forgiveness over confirmation.** Auto-save everything. No "are you sure?" for normal actions; destructive actions (delete session) get undo, not a dialog. The user should never be afraid to tap.
- **P7 — Notepad, not form.** Exercises and sets read as a list, not a spreadsheet. Labels whisper; data speaks.
- **P8 — Wellness and pain are optional, never gates.** Nothing in the logging path ever requires wellness input. The single exception: one-tap sRPE at workout finish, because the load model dies without it.
- **P9 — Guidance over numbers.** No raw metric is shown without interpretation. "Monotony 2.3" is forbidden; "Very repetitive week — your days all look the same" is the product. (Raw values may live behind an "advanced" expander.)
- **P10 — Offline is normal.** Logging works fully offline with zero visible degradation. Sync is silent. The user never sees an error caused by connectivity.
- **P11 — Calm by default, loud by exception.** The Kinetic Manuscript tone: airy, quiet, paper-like. Color and motion are spent only on moments that matter (set logged, warning signal).
- **P12 — Hedged language, always.** We say "possible spike", "worth watching", "consider". We never say "injury risk 82%" or "you will get injured". (See §7 language rules.)

## 7. The interpretation layer — how numbers become guidance

This is the part of the design that makes WOT *WOT* and not "another tracker". It has two halves: **progression** (the payoff — the reason to log) and **signals** (the guardrail). Progression is the primary half; signals interrupt it only when needed. All computation is client-side (per the API contract). All language follows P12.

### 7a. Progression views (the primary half)

These always render when enough data exists — they are not conditional like signals.

**Load progression.** Weekly load bars over 8 weeks, plus a one-line verdict derived from the trend: *building / holding / spiking / dipping*, stated against the user's own 4-week average ("+9% vs your average"). No target implied — the comparison is the user vs. their history, never vs. a prescription.

**Strength progression.** Per key exercise (auto-detected: the user's most-logged strength exercises; the user can pin others): best set trend as a sparkline + direction arrow (↗ → ↘), comparing recent 4 weeks vs. the prior 4 weeks. Tap → full history chart for that exercise (every logged top set, weight × reps over time). This answers "is my leg strength progressing?" at the level athletes actually think in: *the lift*, not an abstract index.

**Balance.** Share of training stimulus per region over the last 4 weeks, from `body_regions` tags — shown against the user's own historical share. Prehab/mobility is a first-class region here, so "am I spending enough time on prehab?" is answerable at a glance ("3% · below your usual 8%"). Optionally switchable to a sessions-per-week view. Deliberately **not** compared against normative ratios ("you *should* do 20% prehab") — the app has no basis for that claim (P12).

**Readiness context.** Fatigue and soreness mini-trends alongside load — not as scores, but so the user can see "load up + fatigue up" coincidences themselves.

### 7b. Signal cards (v1 rule set)

Each signal: **statement → why (numbers, on expand) → suggested action → dismiss.**

| # | Signal | Trigger (v1 heuristics) | Example copy |
|---|---|---|---|
| 1 | Load spike | This week's load > 1.3× trailing 4-week average | "Load rising fast. This week is 40% above your usual. Consider keeping tomorrow easy." |
| 2 | Repetitive week | Monotony above personal 8-week norm | "Very repetitive week — your training days all look the same. Variation protects tissues." |
| 3 | Exposure gap | A previously regular region untouched ≥ 10 days | "No leg work in 9 days. Your usual rhythm is weekly." |
| 4 | Balance drift | A region's share drops well below the user's own historical share | "Prehab is at 3% of your training — your usual is 8%." |
| 5 | Plateau | A key exercise flat/declining ≥ 4 weeks | "Bench press has been flat for 4 weeks. Normal — or time to vary the stimulus." |
| 6 | Progression win | A key exercise up ≥ 2 consecutive weeks | "Squat is climbing — up 3 weeks running. Keep doing what you're doing." |
| 7 | Pain recurring | Same region logged ≥ 2× in 7 days, or severity rising | "Shoulder pain recurring — 3 logs this week." |
| 8 | Stacked warning | Pain region + high regional load in same window | "Pressing volume is high while shoulder pain is trending up. Consider swapping pressing variations this week." |
| 9 | Recovery dip | Fatigue or soreness ≥ 7 for 3+ consecutive days | "Recovery markers dipping for 3 days. Load tolerance may be lower than usual." |

- Max **3 cards** shown, priority order: 8 → 7 → 1 → 9 → 2 → 3 → 4 → 5 → 6.
- Note signal 6 is *positive*: progression deserves airtime too. Signals are not only alarms — they are the app noticing things, good and bad.
- Every card's "why" expander shows the actual numbers. Transparency is how a self-coached athlete learns to trust the app.
- Cards are dismissible. A dismissed card type stays quiet for 7 days unless its trigger strengthens.

### Language rules

| Say | Never say |
|---|---|
| "Load rising fast" | "Injury risk: high" |
| "Squat is climbing — keep it up" | "Great job!! 🎉" |
| "Prehab is below your usual share" | "You should do 20% prehab" |
| "Consider keeping tomorrow easy" | "Do not train tomorrow" |
| "Worth watching" | "Warning!!" / red alarms |
| "Your recovery markers dipped" | "Your readiness score is 61" |

Amber (`#E6AF2E`) for attention cards; secondary blue (`#395F94` — "Analysis") for progression content. Never red. Every signal = icon + words, never color alone.

## 8. States

Empty states are **motivational** in tone (user's explicit choice). Errors never punish.

| Surface | State | Copy / behaviour |
|---|---|---|
| Today — brand new user | empty | "Every training log starts with one session." + Start workout |
| Today — check-in dismissed | quiet | collapses to "+ Check in" text line |
| Active Workout — no exercises | empty | "Add your first exercise →" (no other chrome) |
| History — no sessions | empty | "Nothing logged yet. Your first session will appear here." |
| Insights — < 3 sessions | empty | "Log a few sessions and patterns will start appearing here." |
| Any list | load error | "Couldn't load — tap to retry" inline, content area only |
| Offline | logging | invisible. No banner, no error. Sync retries silently. |
| Sync conflict | — | last-write-wins per resource; user never involved |
| Mid-workout app kill | restore | next open: "Continue Push day (24 min)?" above Start |

## 9. Explicit non-goals (for this design cycle)

Deliberately **not** designed now, so the core loops get all the attention:

- **Plan tab / calendar.** The persona carries their program in their head. "What now" guidance lives on Today; a real Plan feature is a later cycle.
- **Social features**, sharing, feeds.
- **Wearable / Strava import.** HRV stays manual-entry-optional for now.
- **Coach mode** (other people's data).
- **Dark mode.** Deferred; theme tokens must remain semantic so it's cheap later.
- **Body-silhouette pain picker.** Chips first; illustration later if chips underperform.
- **Rest timer.** Lovely, not core. Revisit after Loop 2 ships and feels fast.
- **Bar-path / displacement-level strength modeling** from the brainstorm's level-2/3 formulas. v1 uses volume-load and region exposure only.

## 10. Success metrics — how we know the UX works

| Metric | Target | Why |
|---|---|---|
| Cold open → first exercise on workout | ≤ 10 s | J2, the whole product promise |
| Familiar set logged | ≤ 4 taps + ≤ 2 typed values | J1 |
| Check-in completion time | ≤ 20 s | J6 |
| Check-in completion rate | ≥ 60% of days without any prompting | proves it's frictionless enough |
| Logging frequency | ≥ 4 days/week sustained | the habit *is* the product |
| Workouts abandoned mid-way | < 10% | if high, the logging loop is failing |
| Signal card expand rate | track baseline | do users trust/want the "why"? |
| Signal → behaviour | qualitative review monthly | are cards changing decisions? |

Measure before optimizing. Add lightweight local counters (taps per flow) in the logging loop only — never analytics that slow logging down.

## 11. Resolved contradictions

This design reconciles the prior docs. Decisions recorded so nobody re-litigates silently:

| # | Conflict | Decision |
|---|---|---|
| 1 | Old doc: pre-fill previous weight/reps. User: start blank. | **Blank fields + one-tap-adopt ghost reference** (P3). Blank invites correct data; the ghost keeps last session visible. |
| 2 | Old doc: 4 tabs incl. Log tab. App: 3 tabs, "Log" is a dashboard. | **3 tabs: Today / History / Insights. Logging is a full-screen flow**, not a tab (§3). Tab renamed to "Today" so names tell the truth. |
| 3 | Old doc: pain offered post-session. Data model: one daily log per date. | **Both:** daily check-in on Today + optional post-session feeling — writing to the *same* daily log. |
| 4 | Old doc: dark mode day one. Frontend doc: no dark mode MVP. | **Deferred.** Semantic tokens kept so it's cheap later. |
| 5 | Brainstorm: decision support only. Current Insights: raw ACWR/monotony. | **Signals first, raw metrics behind "Advanced"** (P9, §7). |
| 6 | API requires `type`, `duration`, `srpe` at session creation. UX wants zero setup. | Client creates the session lazily/with defaults and **PATCHes duration + sRPE at finish**. Implementation detail, flagged here so backend expectations are explicit. |
| 7 | Old doc: category browser in exercise picker. | **Recents + autocomplete + inline create only.** Categories removed as overhead (§S3). |
| 8 | Old doc: body silhouette for pain. | **Region chips + free text**, matching the free-text `body_regions` model. Silhouette deferred. |

## 12. Build order

Priority follows the user's stated pains: can't log → home doesn't guide → navigation confusing.

1. **Phase 1 — The Logging Loop.** Active Workout, Exercise Picker, Finish sheet (sRPE), local persistence + silent sync, persistent mini-bar, tab rename to Today. *The app becomes a training log.*
2. **Phase 2 — Today as a guide.** Check-in card + sheet, Start/Resume, week strip, recents, quiet pain line. *The app answers "what now".*
3. **Phase 3 — The interpretation layer.** Progression views first (load trend + verdict, strength progression, balance — §7a), then signal cards (§7b), Insights rebuild, "Advanced" expander, Session detail + "Log again". *The app starts paying the user back — progression before alarms.*
4. **Phase 4 — Alarm loop depth.** Pain trends overlaid on training in Insights, exposure-gap signals, recovery correlations.

Each phase must leave the app shippable and the loops it touches complete — no half-flows in `main`.
